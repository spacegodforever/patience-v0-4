# Structured outputs and audit reports (local branch `feat/structured-outputs-audit-reports`)

Status: **experimental.** Nothing here is a readiness, certification or compliance claim. The audit
log is append-only and tamper-evident (hash chain): edits are detectable, not impossible. Everything
marked *tested* has a test in `tests/test_structured_outputs_reports.py` (offline; sockets blocked).

## 1. Decision outputs: `decision-v1`

`dev_governance/decision_schema.py` defines a strict pydantic model (`extra="forbid"`, `strict=True`,
frozen) describing one gate request: action, proposer/owners, state, payload hash, **policy result with
basis** (each reason classified `policy_rule` / `tier_floor` / `destructive_guard` / `advisory`),
approvals, refusals (from the audit log), execution status, permit state (issued, permit id, key id,
gateway accepted/rejected events), a **confidence** block, `what_could_go_wrong`, a timeline of audit
events (seq, time, event, actor, record hash) and an **`unknowns`** list in which every entry carries
`label: "unknown"` and a source (`advisory` or `system`).

- **Confidence** exists only where the gate has one: the rule-derived advisory level (a function of the
  number of unknowns, "not a probability"). Otherwise `level: "not_applicable"`. Nothing is invented.
- **Missing information is labelled, not guessed**: no advisory generated, audit log not consulted, an
  unrecognized state (mapped to `state: "unknown"`), an executed request with no execute event.
- **Redaction by construction**: only payload *keys* are exported (`payload_values: "withheld"`); the
  signed permit string, claim tokens and grant ids are never part of the model (tested with canaries).
- **Read-only and additive**: `export_decision(gate, rid)` and `GET /v1/dev/requests/{rid}/decision`
  (same caller auth as `GET /requests/{rid}`). It applies the gate's existing expiry check, as `status()`
  already does, and writes nothing else. Existing response shapes are unchanged (tested: key sets of
  `propose()` / `status()`; no existing route changed).
- **Published JSON Schemas**: `schemas/decision-v1.schema.json` and `schemas/oracle-rec-v1.schema.json`,
  generated by `python3 tools/export_schemas.py` from the models. A test requires byte equality with the
  models (so a model change without regenerating fails), checks both forbid additional properties, and,
  when `jsonschema` happens to be installed (it is not a listed dependency), validates real instances.
  The schema files are generated, not hand-edited.

## 2. Accountability gap closed: execute attempts are audited

Previously an execute call on a still-pending request (HTTP 202) or on a denied request (403) left no
audit event. Now:

- pending: `dev.execute.unapproved_attempt` (request id, payload hash, approvals/required);
- denied: `dev.execute.denied_attempt`.

If the audit write fails, `DevGate._audit_required` turns it into `GateError(503)` and the attempt is
refused (fail closed); request state is unchanged. Response bodies and status codes for the normal
paths are unchanged. Other refusals that were already audited are untouched.

Follow-up (`feat/audit-refused-attempts`): the remaining execute refusals (409 already used, not
executable, permit-only, expired / already expired, CAS contention; 501 no adapter) now write
`dev.execute.refused`, and approve-path 409s (expired, not pending, duplicate approver, contention)
write `dev.approve.refused`, each with a `reason` code and `http_status`, fail closed the same way. Both
events count as refusals in `decision-v1` and in audit reports (`http_status` and `request_status` are
on the report allow-list). Tests: `tests/test_audit_refused_attempts.py`.

## 3. Audit reports: `tools/audit_report.py`

Standard library only; it imports no PATIENCE code (tested by AST) and reuses the independent checker
`tools/verify_audit.py` by file path. Library functions `build_report`, `finalize`, `verify_report`,
renderers `to_markdown`, `to_csv`; CLI:

```
python3 tools/audit_report.py generate LOG [--agent A] [--since ISO] [--until ISO] [--allow-key K] [--format json|md|csv] [--out FILE]
python3 tools/audit_report.py verify REPORT LOG        # exit 0 consistent, 1 not, 2 usage/IO
```

Optional read-only endpoint: `GET /v1/dev/admin/audit-report?agent=&since=&until=&format=json|md|csv`,
named approver accounts only (agent bearer tokens are refused; tested). It fails closed with 503 if the
chain does not verify.

**Content**: filters, redaction summary, summary counts (proposed, approved, denied, refused, executed,
execution_failed, execute attempts unapproved/denied, permit issued/used/rejected, oracle events), a per-
request table, and the events (seq, ts, event, category, actor, record hash, redacted data).
**Agent filter**: events whose actor, `agent` or `proposer` is the agent, **plus every event (including
approvals, denials and executions by other people) on a request the agent proposed**.
**Period filter**: ISO-8601; naive times are treated as UTC.

**Chain binding** (`chain` section): number of log records at generation, head hash, head-file hash, the
first/last seq and hash of the records in the period, and a digest over the selected (seq, hash) pairs.
`verify` does four things: (1) runs the independent chain verifier on the log; (2) checks the log still
holds the report's head hash at the same position (the log may have grown, never shrunk or been
rewritten); (3) regenerates the report from the log with the report's own filters, capped at the report's
record count, and requires an exact match (edited, dropped, added or reordered entries, summary, filters
or allow-list changes are detected even if the attacker recomputes `report_hash`); (4) checks
`report_hash`. Tested for: edited, deleted, truncated and consistently-rewritten logs; 12 kinds of report
tampering; log growth after generation; CLI exit codes.

**Redaction (default, `redaction-v1`)**, applied to event `data`:
1. **Deny-list** (always wins, cannot be overridden by `--allow-key`): key names containing token, secret,
   password, api key, private, signature, credential, authorization, cookie, bearer, attestation, nonce,
   or named `permit`/`sig`/`key`/`*_key`/`*_sig`. Identifiers `key_id`, `permit_id` are exempt.
2. **Allow-list**: only a fixed set of known-safe keys is shown (ids, hashes, tiers, counts, reason
   codes, oracle metadata ...). Every other key's value is replaced by `[withheld:<type>]`, so **raw
   payload values are not shown** unless the operator adds the key with `--allow-key`.
3. **Value scrubber** on shown strings: bearer tokens, JWT-like strings, GitHub/Slack/`sk-` style keys,
   AWS access key ids, PEM private keys, `password=`/`token=` pairs, permit-like strings and long
   opaque runs are replaced by `[REDACTED]`.
CSV cells starting with `= + - @` are prefixed with `'` and Markdown table text is escaped.

**Read-only**: generation only reads the log; `--out` is refused if it resolves to the log, its `.head`
or its `.lock` file (tested), and the log bytes are unchanged after generate/verify (tested). A broken
chain stops generation (exit 1, nothing written).

## Architecture decisions

- Additive only: new module, new tools, two new routes, two new audit events. No store schema change.
- Report tool is stdlib-only and separate from the gate so the verifier does not rely on the code that
  wrote the log. The endpoint just loads that same file.
- Verification regenerates rather than trusting stored data, so the report can be an unsigned plain file.
- Permit/gateway events are matched to a request by `request_id` in the audit data.

## Known limitations (honest)

- **Verification needs the original log**; the redacted report alone cannot be re-hashed. A holder of only
  the report can check internal consistency (`report_hash`), nothing more.
- `report_hash` is not a signature. Someone able to rewrite the log, its head file and the report
  together is not detected unless the head hash is pinned outside their reach (`verify_audit.py
  --expect-head`, or compare `chain.head_hash` with a pinned copy).
- Redaction is pattern and allow-list based, best effort. Free-text fields (`reason`, `note`, `error`,
  `reasons`) could still carry an unusual secret format. `--allow-key` widens exposure by design.
- Agent filter relies on `dev.proposed` events in the log; requests proposed before the log was rotated
  are not attributed. Timestamps are the writer's wall clock and are not checked for monotonicity; the
  period range is the first/last matching record, not a proof of contiguity of time.
- Reports and decision exports read the entire log into memory (`audit.read()` and the tool's loader);
  no index. Fine for a small log, not for a large one.
- The decision export uses the existing request state; it does not prove the execution happened on the
  target system (adapters are simulated or dry-run).
- Confidence is the existing rule-derived advisory value, not calibrated. The Oracle's confidence stays
  model-reported and is not part of `decision-v1`.
- Oracle events appear in reports only as categorized, redacted audit events; `decision-v1` does not
  link a request to an Oracle recommendation unless a `routed` event exists (it is not shown specially).
- The `/admin/audit-report` endpoint is read-only but heavy; there is no rate limit.
